Proof of concept · Nov 2026

Giving AI agents a safe room to work in

We built a small rehearsal of how an AI coding assistant could work on real code without being able to do damage. A pretend assistant is given a broken piece of code and asked to fix it. Every step runs inside a sealed, disposable environment, and a manager keeps track of the whole job.

No real AI is involved yet. The assistant is scripted so every run behaves the same way. That lets us test the safety and plumbing on their own, without the AI's unpredictability getting in the way.

The cast

Three systems, three jobs

Temporal

The project manager

Holds the checklist: set up, wait for a human to say yes, try a fix, test it, retry up to three times, clean up. If a computer crashes mid-job, it picks up exactly where it left off.

Substrate

The hotel room with a pause button

Where the assistant keeps its desk. When nobody needs it, the room is frozen: no computer power used, and everything on the desk is exactly where it was left when it wakes up.

OpenShell

The locked exam room

A fresh, sealed room for each check. No internet, no access to anything it wasn't given, and it's destroyed afterwards, so nobody can tamper with the result.

Where it runs

What the two "control planes" are

Everything runs on one laptop. Substrate and OpenShell each get their own small Kubernetes cluster, which you can think of as a miniature data centre running in a box. In Docker you'll see them as poc-substrate-control-plane and poc-openshell-control-plane. The "control plane" is the brain of each mini data centre: it decides what runs where.

One laptop

Manager

temporal server + worker

Runs the checklist and sends instructions to the other two. Has a web dashboard at localhost:8233.

Substrate cluster

poc-substrate-control-plane

Three worker machines that host many frozen or running assistant "rooms".

OpenShell cluster

poc-openshell-control-plane

A gateway that creates and destroys locked sandboxes on request.

The two clusters never talk to each other. Only the manager talks to both.

Combining them

Can Substrate and OpenShell work together?

Yes. They're good at different things, so the useful way to combine them is to give each one the job it's best at.

Built

Each does what it's best at

The assistant lives in Substrate, where it's cheap to keep around and can be frozen while people decide. Every check runs in a fresh OpenShell exam room with strict lockdown. This is the run shown above. Start it with make combined.

Possible

One mini data centre instead of two

Both could be installed into the same cluster. We kept them apart so that when something broke, we knew which one to look at. Worth trying once both are stable.

Not practical

OpenShell running inside Substrate

OpenShell needs a full mini data centre of its own to run in, and a Substrate room is far smaller than that. Nesting one inside the other would add a lot of complexity and give us little in return.

Where this goes next

How we'd expand it

  1. Swap in a real AI modelReplace the scripted assistant with a real one. The model's key stays outside the room, so the assistant can use the AI without ever seeing the key.
  2. Work on real codeClone a real repository into the assistant's room and open a pull request at the end, instead of saving a file on the laptop.
  3. Open the door a crackAllow named websites only, such as a package registry, and keep everything else blocked. Both systems already have the controls for this.
  4. Approvals where people already areSend the "can the assistant start?" question to Slack or a ticket, and let it wait days for an answer at no cost.
  5. Move off the laptopRun the same setup on a cloud Kubernetes cluster and measure the cost of frozen versus running assistants at scale.
